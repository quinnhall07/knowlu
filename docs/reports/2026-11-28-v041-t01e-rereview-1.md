## Adversarial review of the new code

- **(1) The strict read.**
  - The URL is still `/v1/subscriptions/${encodeURIComponent(id)}`, built inside `stripeGetFrom`, which is unchanged:
    `Bearer` plus `stripe-version: STRIPE_API_VERSION`.
  - `a_2xx_read_is_the_subscription_at_the_pinned_version_with_the_id_path_encoded` pins the method, the encoded path,
    the version and the bearer.
  - The key appears only in the request headers. No error carries a message from `fetch` or a body. No body is read on
    a non-2xx, and nothing logs one.
- **(2) The handler.**
  - **Before any effect.** The read sits after the duplicate check, the account check and the `trial_will_end`
    branch, and before `currentUpdatedAt`, `writeEntitlement`, `accountEmail`, `sendEmail` and `recordEvent`. A throw
    therefore answers 502 with nothing written, mailed or recorded, for both events.
  - **The cases that must not change.** I compared each with 1ca6db1c:
    - a 404 still answers 200 `ignored: no subscription on <type>`, with nothing recorded;
    - no string id on the event still leaves `fetchId` a non-string, so the event is ignored;
    - a duplicate still returns before the read;
    - a stale event still reads, then skips the write;
    - the `customer.subscription.*` events never set `fetchId`, so they are unchanged;
    - the `invoice.payment_failed` id expression is the same `??` chain as before.
- **(3) No 502 after a mail.** The read is the only new 502, and it comes before `confirmSubscription`. It cannot follow
  a send.
  - **No endless loop on an event that can never succeed.** A signed event's id cannot draw a 400 from Stripe for a
    reason of its own. A persistent non-404 is a real fault, such as a bad key, a missing permission or a wrong pinned
    version.
  - **The retries are bounded.** Stripe stops retrying when its retry window closes.
- **(4) The tests.**
  - **Coverage.** A 404 (both layers), a 500, a 429, a network throw (both layers), and the redelivery that then
    writes, mails once and records, followed by a duplicate. `subscription_read_test.ts` adds 400, 401, 403, 409, 502,

  - **What no test checks.** No test covers `index.ts`'s wiring; a read of the source confirms `subscriptionReader`

## New findings

- **A. Minor. "A body that is not a Subscription" overstates the check.**
  - **Where.** `handler.ts:56-61` (the `fetchSubscription` doc) and design note `:291-295` (D6b) say a body that is
    not a Subscription throws. `subscription_read.ts:63` checks only that the body is a JSON object.
  - **Scenario.** A 2xx `{}` passes and reaches `entitlementFromSubscription`, which writes a row from empty fields.
  - **Why Minor.** This is not new (the old path accepted any JSON), and Stripe's 2xx for this route is always a
    Subscription.
  - **Fix.** Either add `body.object === "subscription"` with one test case, or change the words to "a JSON object".
- **B. Minor. A 404 on a read event is still silent** (`handler.ts:312`).
  - **Why a 404 here means misconfiguration.** Stripe keeps cancelled subscriptions retrievable. A 404 for a
    subscription that a checkout or an invoice names therefore almost always means a key for the wrong mode or the
    wrong account.
  - **Scenario.** Production is given a test-mode secret key. Every confirmation and every `invoice.payment_failed`
    read is answered 200 `ignored`, with no log line. The `customer.subscription.*` events keep entitlements right, so
    nothing else shows the fault.
  - **Not a regression.** It behaves as before the fix, and as ruled.
  - **Recommendation.** One log line naming the event type only (`stripe-webhook: <type>: Stripe has no such
    subscription`), as a follow-up.

## On the implementer's two concerns

- **A lasting non-404 failure now shows as failing deliveries.** This hides no defect. It makes a real outage visible
  (a rotated key also breaks the other Stripe-calling functions). The retries are bounded by Stripe's window, and no
  mail can be sent twice by it. A key fixed inside that window now gets the confirmations out, where before they were
  lost.
- **Any 404 counts as "no subscription".** This hides a misconfiguration, not a code defect. It is as before, and
  finding B is the cheap way to make it visible.
