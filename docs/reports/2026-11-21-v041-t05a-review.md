### The 30

- The window is `ahead >= N·day && ahead < (N+6)·day` (`billing-jobs/handler.ts:84-87`, the note's
  `:532`).
  - At N = `MOVE_NOTICE_MAX_DAYS` = 24 the latest notice goes out strictly under 30 days ahead.
  - At N = `MOVE_NOTICE_MIN_DAYS` = 7 the earliest goes out exactly 7 days ahead.
- `noticeBounds()` walks whole days from 24 while the window is open and stops at 30. The test then
  checks, for every N from 7 to 24, that nothing goes out under 7 days or at 30 days or more. It also
  checks that both edges are tight. So the derivation is right.
- It uses the same relation `catalogProblems` enforces: N in [7, 24] (`price_catalog.ts:130-131`,
  `:156`), with the handler's +6 turning 24 into 30. That is the relation the comment at `:128`
  states.
- Each handler change below fails a test without any catalog edit:

| Change | What fails |
|---|---|
| The window widened to N+7 | `max` becomes 31, so the page check fails. |
| The window narrowed so it never opens at 24 days | `max` stays 24, so the page check fails. |
| The lower edge moved later | `inMoveWindow(7·day, 0, 7)` fails. |
| The lower edge moved earlier | The "nothing earlier than 7" loop fails. |
| `MOVE_NOTICE_MAX_DAYS` raised to 25 | `max` becomes 31, so the page check fails. |

     check the version as `These terms are version 2026-11-21` in that text, or keep the `<strong>`
     form on the raw text and add the comment strip.

   - Failure scenario: a stray old price written as `&#36;9.99`, `$ 9.99` or `$.99` is invisible to
