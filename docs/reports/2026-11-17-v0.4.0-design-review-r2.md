## 2. New problems from the revision

### Important (all fix in text)

**N1. Waiting shows every "increases" amendment twice, and the first copy cannot be acted on.**
- *Where:* §4 Home, "Waiting: cards" ("`S.must_do.amendments` first, then `S.decisions.cards`"), and
  "Waiting: header" (which lists `hidden_amendments`).
- *Conflicts with:*
  - `read_approvals` pushes **every** pending amend to `cards` as well as to `amendments`. The card
    filter is `kind != "events-digest"` (`engine/src/surface.rs:1649-1678`).
  - `must_do.amendments` is the "increases" subset of the same notes (`surface.rs:1003`).
  - `AmendCard` has no `id`, only `proposal_path` (`surface.rs:897-904`), and `decide` needs an id
    (`app/src/commands.rs`, `decide(id, verdict, …)`).
  - The shipped deck draws `d.cards` whole (`console.js:361`).
- *Scenario:* an agent's "increases" amend appears as two cards in a row. Approve on the first has no
  id to send, so it fails or does nothing. `hidden_amendments` would then claim "N amendments the deck
  does not surface" about cards that are on screen.
- *Cause:* this is r1's error. I3 said non-increasing amendments had no surface, but they are in
  `decisions.cards`.
- *Fix:* Waiting cards are `S.decisions.cards` only. Drop `must_do.amendments` from Waiting, or use it
  only as a marker on the task row. Drop `hidden_amendments` from the header.

**N2. Starting the window hidden does not stop the flash for maximized or small-screen students.**
- *Where:* §3 Config and Window state, and D6 ("Rust maximizes on launch when the monitor's work area is
  smaller").
- *Conflicts with:*
  - The flags still include `MAXIMIZED`. Restore calls `maximize()` at window-ready (plugin 2.4.1
    `src/lib.rs:218-220`).
  - tao applies `MAXIMIZED` with `ShowWindow(SW_MAXIMIZE)` and does not check visibility
    (`tao-0.35.3/src/platform_impl/windows/window_state.rs:377-386`). That makes the hidden window
    visible.
  - D6's maximize-if-small goes the same way.
- *Scenario:* a student who closed the window maximized, or anyone at 150% on a 1920 x 1080 screen,
  sees the window before WebView2 paints. With `backgroundColor` gone, that frame is the default
  background, and the bar's "no flash in either theme" fails.
- *Fix:*
  - Build both plugins with `.skip_initial_state("main")` (`lib.rs:369-371`).
  - Do restore, maximize-if-small and `show()` together, after first paint: from the page through a
    command, or in Rust when the page signals.
  - The 3 s fallback takes the same path.
  - State that the fallback is in both builders (`run_shell` shows the wizard too).

**N3. The pre-tag gate cannot pass with a merge commit.**
- *Where:* §9 "Pre-tag gate" ("M10's proof ran on a build of that SHA … any later commit restarts the
  gate"), and §10 (proof before the PR is ready).
- *Conflicts with:* CLAUDE.md, where the live proof comes before a PR is called ready. Main's merge
  commit is a new SHA that did not exist when the proof ran.
- *Scenario:* proof on the branch head, then merge, then a new SHA, then the gate restarts, then
  another proof. Every round produces a new commit, so the gate never closes. In practice it would just
  be skipped.
- *Fix:* the gate accepts a proof on any commit whose tree equals the tagged SHA's tree
  (`git rev-parse <a>^{tree}` = `<sha>^{tree}`). Main must not move between the proof and the merge.
  CI and `-DryRun` still run on the exact SHA.

**N4. The shared pin module will put warnings in the build.**
- *Where:* §8 "Pin files, one per lane" (`app/tests/ui_common/mod.rs`, with `mod ui_common;` in each
  file).
- *Conflicts with:* each `tests/*.rs` file is its own crate. A helper one lane does not call is
  `dead_code`, so seven of the eight files warn, and 0 warnings is part of green (CLAUDE.md).
- *Precedent in this repo:* `app/tests/support/slot_rig.rs:6` is `#![allow(dead_code)]` and is included
  by `#[path = "support/slot_rig.rs"]` (`app/tests/account.rs:2842`).
- *Fix:* `app/tests/support/ui_common.rs`, with `#![allow(dead_code)]` and `#[path]`, following that
  precedent.

**N5. The skeleton has one sheet host, no stacking rule, and nowhere for the I5 Settings layer.**
- *Where:* §2 Files (`#sheet`), §5 (re-consent; "Settings opens `#settings/data` in a layer
  **above** the sheet"), and the M2 row (`#center`, `#panel`, `#sheet`, `#boot`, `#top-note`).
- *Conflicts with:*
  - The shipped rules: two panels never stack, and re-consent stands down while Settings, Report, mail
    progress, mail applied or upgrade is open (`console.js:3137-3141`). The upgrade overlay is never
    raised over Settings (`console.js:2979`).
  - Six sheets (re-consent, sign-in/upgrade, week setup, mail progress, report, the update or
    Answer form) share one host. Settings is a `#center` route, which sits below `#sheet`.
- *Scenario:* M5b cannot draw Settings above the re-consent sheet without editing `index.html`, which
  only M2 may edit. Or two sheets render into `#sheet` and overwrite each other, for example the
  week-setup sheet and re-consent on a first day after a privacy bump.
- *Fix:* M2's skeleton adds a `#layer` host above `#sheet`. §5 states the sheet order (re-consent,
  then sign-in/upgrade, then week setup, then mail progress, then report) and that only one draws at a
  time. The re-homed pins carry the stand-down rule.

### Minor (all fix in text)

- **N6. The changed permission pin has no home after the swap.**
  - Where: §8 "Kept" moves five tests to `bundle_config.rs`. M3b changes
    `the_page_is_granted_no_updater_permission` inside `static_assets.rs`, and M8b deletes that file.
  - Scenario: the exact-list "no updater permission" pin is deleted with the file.
  - Fix: name it as moving to `window_chrome.rs` or `bundle_config.rs`.
- **N7. The page's class-matching rule is not the engine's.** This settles M2's `unverified` item
  (details in section 3).
  - The difference only affects colour and Meets, so a neutral draw is honest.
  - Fix: either (a) M7 adds `codes: Vec<String>` to `CourseEntry`, filled from `code_table`'s claims
    for that slug, and the page matches against those; or (b) the spec says the rule matches only
    wizard-made notes and that the rest draw neutral.
  - Recommend (a). It is about five lines inside M7, which already reads `courses/`.
- **N8. The handle types differ between tauri and the app.** tauri's `WebviewWindow::hwnd()` returns
  windows 0.61's `HWND` (`tauri-2.11.5/src/window/mod.rs:1668`). The app's crate is 0.62
  (`app/Cargo.toml:92`; both versions are in Cargo.lock). M3b converts through the raw pointer. Nothing
  in `app/src` calls `hwnd()` today. `Win32_Graphics_Dwm` exists in 0.62.2 and pulls in
  `Win32_Graphics`. Its constants are `DWMWA_BORDER_COLOR` = 34 and `DWMWA_COLOR_NONE` = 0xFFFFFFFE.
- **N9. "First frame has painted" is not specified.**
  - Where: §3, "shown after `prefs.js` … and the first frame has painted".
  - The hidden host window has the WebView2 controller set visible (`wry-0.55.1/src/webview2/mod.rs:544`).
    Whether `requestAnimationFrame` fires while the host HWND is hidden is not settled by code.
  - Scenario: if it does not fire, every launch waits for the 3 s fallback.
  - Fix: show after the theme is set and `DOMContentLoaded` plus one rAF with a short timeout. Step 10
    of the proof records time-to-show.
- **N10. "Clear through" can sit above must-do rows.**
  - Must-do is slack ≤ 0, so a task due Friday that must start today is in Do today while bucket 0 can
    be empty. Home would then say "Clear through Thu" above its own Do today list.
  - Fix: show the line only when Do today has no unchecked rows.

## 3. The three remaining `unverified` items, settled

1. **Does `compact(slug|title)` equal the engine's `course_key` table in every vault (§4)? No.**
   - `code_table` claims codes from each course note's `code`, `title` and `name` through
     `to_code_exempt`, which extracts a code from text and skips term prefixes. It also claims from the
     slug and from `config/ingest.yaml`'s `course_map` (`engine/src/commitments.rs:754-778`).
   - Classification looks titles up in that table (`commitments.rs:1155-1157`). `course_key` maps
     through it (`:2531-2537`).
   - The page rule agrees on wizard-made notes: `title` is the human code (`app/src/scaffold.rs:830`),
     and `compact("cs-100")` = `compact("CS 100")`. It misses a note titled "CS 100 – Intro …", a
     commitment written with the LMS `code:`, and `course_map` keys. See N7.
2. **How the privacy cross-check normalises entities (§6): it does not.**
   - The pin takes the raw `<p>` line from `site/privacy.html`, trims `<p>` and `</p>`, and requires
     `var PRIVACY = "<sentence>";` byte for byte (`app/tests/static_assets.rs:1048-1060`).
   - The sentence has no entities (`site/privacy.html:14`; matches `console.js:3318`).
   - The re-homed pin should do the same raw comparison against `wizard.js`. The "decodes the same way"
     clause can be deleted.
3. **Where the window-state file lives (§10 step 11): `%APPDATA%\com.knowlu.desktop\.window-state.json`.**
   - `DEFAULT_FILENAME` (plugin 2.4.1 `src/lib.rs:36`) is joined to `app_config_dir()` (`:122`, `:515`).
   - `app_config_dir` = `dirs::config_dir()/<identifier>` (`tauri-2.11.5/src/path/desktop.rs:238-241`),
     which is Roaming AppData on Windows.
   - The file is per Windows user, not per profile, so a scratch profile does not reset it.

## For Quinn (decisions, each with a recommendation)

**Q-A. Should the re-consent sheet hide today's page?**
- Today's panel "never hides today's page" (`console.js:3116`).
- The shipped and pinned change text tells the student "Until you accept, Knowlu keeps today's page
  and your calendar up to date" (`console.js:3129`; pin
  `the_panels_changes_describe_this_privacy_version`, `static_assets.rs:3418`).
- r2 makes the sheet full-window, so the day cannot be seen at all until the student accepts or deletes
  their data.
- **Recommend:** keep the shipped behaviour. Show a non-dismissable panel over a visible, usable Home,
  with start controls locked as now. That matches the words the student is shown. The alternative makes
  accepting the price of seeing their own vault, which the current text does not say.

**Q-B. Does the ported knowlu.com offer a download in v0.4.0?**
- The live, signed site is early access with a mailto form and no installer link. M13 adds
  `releases/Knowlu-setup.exe` to keep a `site.rs` pin, which edits the page Quinn signed, the same
  objection §13 raises against changing prices on it.
- **Recommend:** decide with Q1. If v0.4.0 is open to new students, add the link. If it stays early
  access, leave the index as signed and drop the download-link pin, saying why in the test.

**Q-C. The updater window between publish and step 12.**
- A 0.1.5 install downloads and stages 0.4.0 on its own daily check and offers "Restart to update"
  (`app/src/updates.rs`). Step 12 (the signed updater path) can run only after `latest.json` is live.
  Students can therefore take 0.4.0 before step 12 has run.
- Step 11 tests the same installer, so the risk is small.
- **Recommend:** accept it, and run step 12 in the first hour after publish, with `latest.json`
  rollback ready.
