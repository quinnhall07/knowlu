## Findings

1. **Important. A transient Stripe error on the fetch means the confirmation is never sent, and nothing is logged.**
   `handler.ts:286-295` with `_shared/stripe.ts:125`.
   - **The cause.** `stripeGetFrom` turns every non-2xx into `null`: a 429, a 500 or a version error alike. The handler
     then answers 200 `ignored: no subscription on checkout.session.completed`, so Stripe never retries.
   - **Why it matters now.** Before this task that path lost only one redundant entitlement write, and
     `customer.subscription.created` wrote the same row. The confirmation has no second source: no other event sends
     it.
   - **Scenario.** A student subscribes during a Stripe API blip, and the fetch gets a 503. The webhook answers 200,
     no mail goes, no log line is written, and the terms' promise is broken without anyone knowing.
   - **Why it is not the implementer's fault.** The brief mandates this ("None: answer as today"), so it is not a spec
     failure.
   - **Recommendation for the controller:**
     - at minimum, one log line with the account id when a checkout event's fetch comes back empty (`handler.ts:295`);
     - better, a follow-up where `index.ts`'s `fetchSubscription` treats only a 404 as "none" and throws on anything
       else, so Stripe retries. That needs a new additive helper beside `stripeGetFrom`, since its existing export must
       not change.
2. **Minor. The design note still says C8 is not in this lane, and D11's lead-in now contradicts its own item.**
   - **The two places.** §7 (`docs/specs/2026-11-19-v041-pricing-design.md:1163`) still lists "**C8**, the
     confirmation email" under "Not in this lane". D11 (`:469-470`) introduces its list as "left out, because this
     release builds none of their code". Its C8 item now says it is built.
   - **What is actually true.** The published terms already carry the sentence (`site/terms.html:90`).
   - **Scenario.** The next planner reads §7, concludes C8 is still owed to v0.5.0, and builds a second confirmation.
   - **The smallest true edit to §7** (the controller's, since the brief barred it):
     `- **C8**, the confirmation email. *Changed 2026-11-27:* built in this lane (D6b).`
   - **For D11, if the controller wants it exact:** `*Changed 2026-11-27:* the published terms carry it
     (site/terms.html:90), and D6b now builds it.`
3. **Minor. The test does not prove the write came before the send.**
   `handler_test.ts:1366` asserts `written.length === 1` after the 502, but not the order.
   - **Scenario.** An implementation that tried the send first and wrote the entitlement only on failure would still
     pass. On success, that implementation would not write at all, and other tests would catch that, but the
     failure-path order the brief names is unasserted.
   - **Fix.** Inside the refusing `sendEmail`, assert `seen.written.length === 1` before rejecting.
4. **Minor. The `payment`-session case checks only the mail.** `handler_test.ts:1273-1279` checks that nothing was mailed
   and no address was looked up. It does not check the body `{ok:true, confirmed:false}` or that the event was recorded.
   - **Scenario.** A change that made a payment session return early without recording would pass this test.
5. **Minor. A stale comment.** `handler.ts:59`: the `accountEmail` doc on `Deps` still says "the reminder goes only to
   the account's own address". It now serves both mails.
6. **Minor. One known limit is understated.** D6b's known limit names only two deliveries processed at the same
   instant. There are two more ways one event can be mailed twice:
   - the email provider accepts the mail but its response is lost, so the send throws and Stripe's retry mails again;
   - the record fails after a send, then Stripe redelivers the event anyway, which it can do even after a 2xx.

   Both apply equally to D6. A possible follow-up, not for this task: send the event id as the provider's idempotency
   key from `index.ts`. That closes the same-day cases. It does not close a retry more than a day later.
7. **Minor. A subscription that is not started at checkout never gets the confirmation.** One that is `incomplete` at
   checkout completion and becomes `active` later is never mailed, because only `checkout.session.completed` sends.
   - **Why it is Minor.** The brief mandates this, and card checkouts complete as `trialing` or `active`.
   - **Recommendation.** Note it in D6b's known limits if any delayed payment method is ever enabled.
