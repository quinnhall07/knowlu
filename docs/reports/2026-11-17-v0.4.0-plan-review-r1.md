## Blocking

**P1. Page modules have no way to load (fix in text).**
- *Where:* plan §2 and §3, T5b ("`next/index.html` … nothing but T5 edits it"), T7-T22 (each owns new
  `pages/*.js`, `carried/*.js` and `css/*.css`), and T5a's `every_script_and_link_resolves`.
- *The gap:* nothing says how a later task's `home.js` or `home.css` gets a `<script src>` or `<link>`.
  The CSP admits only `'self'` scripts and IPC `connect-src` (`app/tauri.conf.json:10`). Only T5b may
  edit `index.html`, and `boot.js` and `router.js` are T5b's too.
- *Scenarios:* either way it fails.
  - T5b's `index.html` names only the shell files. T7 merges a `home.js` that nothing loads. The DOM
    check can only pass if T7 edits `index.html` (an ownership breach) or the harness injects the
    script (a test that proves nothing the app does).
  - T5b's `index.html` names all of T7-T22's files ahead of time. `every_script_and_link_resolves` is
    then red on `feat/v0.4.0-ui` from T5b's merge until T22's, which breaks §2's rule that the branch is
    green at every commit.
- *Fix:* T5b creates an empty placeholder for every module and stylesheet that §4's table names, and
  lists them all in `index.html`. A placeholder can be a one-line `/* T7 owns */`, which passes every
  `ui_shell` pin. Each page task then replaces only its own placeholders. Ownership is sequential (T5b
  first, then the task), never parallel, and the resolve pin stays green throughout. §4's Owns column
  gains "(replaces T5b's placeholder)".

## Important (all fix in text unless marked)

**P2. T5a's red pins can merge alone.**
- *Where:* §4 lists T5a and T5b as separate rows, with T5a "After T0 (may run in G1)" and its review
  "with T5b".
- *Scenario:* if T5a merges before T5b exists, `ui_shell.rs` fails on `feat/v0.4.0-ui`, because
  `the_skeleton_has_every_host` finds no `next/index.html`.
- *Fix:* T5a and T5b share one branch (`v040/t05-shell`), with the red commit first and the green
  commit after, merged once. T1, T6 and each page task already work this way.

**P3. Three pins assert files that another parallel task owns.** Each would stay red on its own branch
until the other task merges, so its red window cannot close there.
- **T8 and the deck.** `waiting_hosts_the_deck_one_card` (T8, wave B) needs the deck renderer, which is
  `carried/deck.js` (T15, also wave B, not in T8's "After").
- **T16 and the Settings rows.** The re-homed `the_settings_panel_has_its_rows_and_one_way_in` (T16,
  wave C) asserts `set-updates`, `set-account`, `set-report`, `set-delete` and `set-diag`
  (`app/tests/static_assets.rs:1067-1072`). T19 and T20 render those ids in wave D.
- **T20 and the start controls.** The re-homed
  `every_start_control_reads_the_owed_flag_and_a_throw_never_strands_it` (T20) lists controls that T17
  (Connect, Rotate, Gmail) and T19 (Sync now) render. All three run in parallel in wave D.
- *Fix:*
  - Each re-homed pin asserts only its own task's files: T8 that it calls `KnowluSlots.deck`, T16 its
    own sections, and T20 that every control marked `data-start` goes through `KnowluKit.owed`.
  - The cross-file "every one exists" assertions move to `ui_swap.rs` (T23), where every file is present.
  - Or give T20 "After T17, T19".

**P4. The note asks for a `google_status` call at launch that a re-homed pin forbids.**
- *Where:* note §4 Shell and plan T5b ("`google_status` at launch and on Settings only"). Against them,
  T5a re-homes `the_launch_account_check_does_not_reach_google_status` into `ui_shell.rs`.
- *Conflicts with:* that pin (`static_assets.rs:1904-1915`) requires the launch account check to reach
  `google_status` only behind the Settings-open guard, the shipped spec §4.4 rule
  (`console.js:2347-2352`). The "at launch" part entered the note through r2's wording of M5, which
  intended "Settings mount only".
- *Scenario:* T5b calls `google_status` at boot, the re-homed pin fails, and the task cannot go green
  without editing the pin, which §9 forbids.
- *Fix:* plan §11 settles it as "Settings mount only, as shipped". The Status list's Google line shows
  what the last Settings visit read, or nothing. The note's §4 wording follows at the next docs pass.

**P5. Merging with `--no-ff` puts every red commit into the branch's history.**
- *Where:* §2 says "`--no-ff`, one merge per task" and "the integration branch and the PR are green at
  every commit".
- *The gap:* a `--no-ff` merge keeps the task branch's commits, red ones included, as second-parent
  ancestors on `feat/v0.4.0-ui`, and later on main through the PR merge. "Green at every commit" holds
  only along the first-parent chain.
- *Scenario:* a later `git bisect` on main lands on a `red: …` commit and reports a false culprit.
- *Fix:* say "green at every first-parent commit" and use `git bisect --first-parent`. Or squash each
  task branch into one commit at merge, with the red and green SHAs kept in the ledger. Either fits
  CLAUDE.md. Pick one in §2.

**P6. One red dispatch per wave writes into four branches.**
- *Where:* §4 ("one `test-writer` dispatch writes the red files for the whole wave") and §2 (each task
  branch is cut from the integration head at dispatch).
- *The gap:* a single dispatch must commit four red files and four check scripts into four worktrees
  or branches, and those branches may have different bases. Wave B's T8 waits for T7, while T14 and T15
  wait only for T5c, so the batch also holds back tasks the "not a barrier" rule lets start early.
- *Fix:* say the dispatch commits each file in its own task worktree, which is cut before the
  dispatch, one red commit per branch. Batch only tasks whose "After" is already merged.

**P7. A "Google-served" PT Serif Caption is still a subset.**
- *Where:* T1 ("unmodified upstream or Google-served files (no subsetting)") and T4 ("replace the PT
  Serif Caption subset with the unmodified file").
- *The gap:* the CSS2 endpoint serves per-script subsets. That is how the current Instrument Sans files
  were fetched (`app/static/fonts/SOURCES.md:3-7`, the `latin` subset). The site's 235-glyph PT Serif
  Caption, which keeps the reserved name, is most likely exactly that file.
- *Scenario:* T1 and T4 fetch from `fonts.gstatic.com` and get the same kind of subset, so M11's RFN
  concern stands under a "fixed" label.
- *Fix:* for PT Serif Caption, name the full file from the google/fonts repository (`ofl/ptserifcaption/`)
  and its OFL. The acceptance checks that the file's hash matches that repository's.
