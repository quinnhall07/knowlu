## Findings

**M1. Minor: after a refused checkout, the refusal stays on screen when the next press succeeds.**
`app/static/js/wizard.js:711-713`.
- Scenario: the student presses Yearly and the server answers 409 "Knowlu's prices or terms have changed…".
  The step asks again and gets the new offer, and the student presses Yearly again. The payment page opens,
  and "Waiting for the payment page in your browser…" appears. The 409 sentence stays in `#wiz-error`
  (`role="alert"`) above it.
- This was true before T4 too, but T4 makes refuse-then-retry a designed path. The sheet clears its sentence
  (`say("")` at `account.js:202`).
- Fix: `WIZ.error = "";` beside `WIZ.checkoutOpened = true;`.

**M2. Minor: a second press while the first is in flight opens a second payment page.**
`app/static/js/wizard.js:700-717`, `app/static/js/carried/account.js:193-217`.
- Neither handler has a busy guard, and the buttons stay enabled once a checkout has opened.
- Scenario: a double-click on Yearly, or Yearly then Every 4 weeks, sends two `open_checkout` calls. Two
  Stripe sessions open in two tabs, and two entitlement polls run.
  `billing-checkout`'s live-subscription refusal (`handler.ts:203-204`) runs only when a session is created,
  so two sessions made before either is paid are both payable.
- This was true before T4 (two wizard buttons, one sheet button). T4 now gives the sheet two plans to press.
- Fix: a `checkoutBusy` flag on `WIZ` and on `UP`. Set it before `checkEntitlement()` and clear it when
  `open_checkout` answers. Render the plan buttons disabled while it is set.

**M3. Minor: a plan press that the host rejects says nothing in the wizard.**
`app/static/js/wizard.js:716`.
- Scenario: the shell host does not answer `open_checkout`. Its error is the three-key unreachable shape,
  which `invoke` turns into a throw. The student presses Yearly, and `.catch(function () {})` swallows the
  throw. The button stays enabled, and no sentence appears.
- A missing argument cannot occur, because `offerFrom` checks every field `open_checkout` needs. The sheet does
  not have this problem: `KnowluData.call` resolves, so `r.ok` is false and `r.error` is shown.
- This was true before T4.
- Fix: `.catch(function () { WIZ.error = UNREACHABLE; renderWizard(); })`, as the sign-in handlers do at
  `:661` and `:676`.

**M4. Minor: a plan whose `lines` is empty counts as offered.**
`app/static/js/wizard.js:431`, `app/static/js/carried/account.js:158`.
- `[].every(...)` is true. If the server sends `lines: []` for a plan, the button is enabled with no figure
  beside it, against D9's "no offer, no figure".
- Stripe's page still shows the price before any charge, and the server writes the lines, so this needs a
  server bug to happen.
- Fix: add `p.lines.length > 0 &&` to both guards, so that offer reads as missing and gets the update sentence.

**M5. Minor: the sheet's failure states have no DOM check.**
`scripts/ui-fixture/checks/t20.py:82-112`.
- t20 runs only the offer-held path. The sheet's `offerFrom` is not the wizard's: it has the extra
  `KnowluData.last` guard. The Rust pins match its source text, not its behavior.
- Scenario: a later edit makes that guard always false. Every server refusal in the sheet would then read
  "Check your connection", and no test would fail.
- Fix: in `check_upgrade`, stage `OFFER_FAILS["refused"]`, then `["unreachable"]`, then `["no-four-weekly"]`,
  as t21 does. Assert that both buttons are disabled and check `#up-sub-why` before staging `OFFER`.

**M6. Minor: the t16 generator would put the old plan back.**
`scripts/ui-fixture/checks/t16.py:66`.
- `ACCOUNT_MEMBER` still says `"plan": "monthly"`. `t16.py --make` would rewrite
  `t16-settings-answers.json:10` to `monthly`, and t16's new assertion would then fail. The failure is loud,
  not silent. The same constant feeds the t17 to t20 sets.
- The brief allowed only one assertion in t16.py, so this is a follow-up, not a T4 defect.
- Fix: set `ACCOUNT_MEMBER`'s plan to `four_weekly` and regenerate, in a task that owns the generator.
