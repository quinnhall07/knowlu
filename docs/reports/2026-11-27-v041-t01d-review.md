## Findings

### 1. Important: a 2xx whose body is JSON `null` is read as "Stripe does not know this subscription", and the account is purged

`cloud/supabase/functions/account/stripe_delete.ts:112`

This breaks binding constraint 3 and the brief's rule 5: a delete never proceeds past a subscription whose state is
unknown.

`deleteFetch` hands every 2xx through untouched. `stripeGetFrom` then returns `await res.json()`, and for the body
`null` that is `null`. `subscriptionStatusFrom` treats every `null` from `get` as the missing-id case
(`if (sub === null) return null;`). So a 200 with body `null` means the same thing as a 404 `resource_missing`.
`handler.ts:113` then logs "does not know the stored subscription" and goes on to the purge, the tombstone and the
login delete.

Failing scenario: an egress proxy, a Stripe incident, or a future change to the fake or real fetch answers 200 with
the literal body `null` while the subscription is `active`. The account is deleted, and the subscription renews and
charges the card every 4 weeks with no account left to cancel it from.

Every other 2xx shape fails closed with the 502:
- a non-JSON body;
- an empty body or a 204;
- an array, a number, a string or `true`;
- an object with no `status`, or with a status that is not a string.

The test table in `stripe_delete_test.ts` (around line 136) covers "a 200 with no status" but not "a 200 whose body
is null".

The likelihood is low, but this is exactly the fall-through the rule forbids, and the fix is a few lines:
- `deleteFetch` (the read's instance) records that it passed a `resource_missing` 404 through, for example with a
  per-call flag or an `onMissing` callback.
- `subscriptionStatusFrom` returns `null` only when that record is set.
- A `null` with no record throws the 502.
- Add a test case: `["a 200 whose body is null", fakeFetch(200, "null")]`, which must give the 502.
- Optionally, also require that `sub` is a non-array object before `status` is read.

### 2. Important (a decision, outside the brief's letter): the stored id can lag Stripe just as the status can, and T1d now purges past a stale ended id

`cloud/supabase/functions/account/handler.ts:98-113`

This affects the rule that matters: nobody is charged after their account is gone.

The brief rules out `entitlements.status` because "the row can lag Stripe". `entitlements.stripe_subscription_id`
is written by the same webhook and can lag in the same way.

Failing scenario:
1. A former subscriber's subscription has ended, and the row holds its id with status `canceled`.
2. Checkout lets them subscribe again: D5 blocks only live statuses, and `billing-checkout/handler.ts:326` lets an
   ended one through.
3. The new subscription's webhook has not landed yet, or keeps failing.
4. They press Delete my data. The delete reads the old id, Stripe answers `canceled`, and the account is purged.
5. The new subscription keeps charging.

Before T1d this delete stopped at the 502 (Stripe refused the update on the old id), so T1d opens this path, even if
narrowly. A related gap existed before T1d: an account with a Stripe customer but no stored id yet skips Stripe
altogether.

Recommendation, for the controller to rule on: when the stored subscription reads as ended or missing, or when there
is no stored id but `accounts.stripe_customer_id` is set:
- List the customer's subscriptions (one versioned GET, by customer, all statuses).
- Cancel at period end every one that is not `canceled` or `incomplete_expired`.
- Stop with the same 502 if the list cannot be read.

This goes past the brief's "one read of that subscription", so it is a brief amendment, not an implementer fix.
Shipping T1d without it is defensible if the controller accepts the webhook-lag window. If so, say so in the lane
note.

### 3. Minor: the other-mode guard depends on Stripe's wording, and fails toward the brief's own rule

`cloud/supabase/functions/account/stripe_delete.ts:33, 79`

The ruling is right. A key of the wrong mode gets a 404 `resource_missing` back. Reading that as "nothing to cancel"
would delete an account whose subscription in the other mode still charges, so stopping is the safe answer. The
match is on Stripe's present text ("a similar object exists in live/test mode").

If Stripe rewords that text, the guard stops matching and the behavior falls back to the brief's rule 3 exactly. It
never fails toward something less safe than the brief asked for. A null or absent message also falls back to rule 3.

A key belonging to a different Stripe account (not a different mode) answers a plain `resource_missing`, and the
delete goes on. The brief accepted that. No change is asked for; this is recorded so nobody reads the guard as
covering it.

### 4. Minor: the logged, redacted Stripe body can still carry the platform's own Stripe identifiers

`cloud/supabase/functions/account/stripe_delete.ts:30`

`redactStripeText` removes subscription and customer ids, emails and keys, and it cuts the text after redacting, so
a cut can never expose part of an id. Stripe's `request_log_url` and messages can still carry a request id, the
platform account's own id, or the ids of other objects (an invoice or a payment method). None of these is a
subscription or customer id, so the brief's rule holds, and the logs are the function's own.

If the lane wants the stricter reading ("no Stripe object id in a log line"), widen the pattern to Stripe's general
`prefix_alphanumeric` shape, or drop `request_log_url` before logging. This is optional.

## Checked and clean

1. **Ended or unknown subscriptions no longer block the delete.** `canceled` and `incomplete_expired` skip the update.
   A 404 `resource_missing` reads as `null` and logs one `console.warn` with no id. The handler tests prove both, and
   the order of effects.
2. **Every other status still gets the cancel first.** `trialing`, `active`, `past_due`, `unpaid`, `paused`,
   `incomplete`, and a status the code has never seen, all get `cancel_at_period_end=true` before the purge. The
   tests show the order: the read, then the cancel, then the purge.
3. **Other failures stop the delete, apart from finding 1.** Each case below throws the same 502 before the purge, and
   none falls through to it:
   - a thrown fetch (logged by error name only, because the message carries the URL);
   - every non-2xx: 400, 401, 403, 404 other than `resource_missing`, 404 other-mode, 429, 5xx, and a 3xx that is
     not followed;
   - a non-JSON or empty 2xx (`or502`);
   - a 2xx with no string status.

   Redirects are followed by the platform's default, and a redirect loop surfaces as a thrown fetch, so the 502.
   `asResponse` in `index.ts` passes the thrown 502 back unchanged. The update's 404 is never passed through. The
   handler tests pin the order: a failed read leaves only the read, and a failed update leaves the read and the
   cancel, with no purge, tombstone or login delete.
4. **The implementer's two additions are sound.**
   - **The other-mode stop:** see finding 3.
   - **The id-shape stop:** `^sub_[A-Za-z0-9]+$` matches Stripe's subscription ids and follows review M5's rule in
     `billing-checkout` (line 83). An empty column is still "no subscription". Any id this rejects already ended in
     a 502 before T1d, so nothing that worked before stops working. The check logs no id.
5. **Version header, error body, logs.** The pinned `Stripe-Version` goes on the read and on the update, and the
   tests assert it against `STRIPE_API_VERSION`. The caller only ever receives the fixed 502 text. No id reaches a
   log line from this code. The update now runs over a wrapper that throws before `stripePostFrom`'s own log line
   (which prints the path, and so the id) can run. That is an improvement on the code before T1d.
6. **Scope.** `_shared/stripe.ts` is untouched. All five changed files are under `account/`. The README does not
   describe the delete's Stripe step, so leaving it alone is correct.
7. **Public repository.** The test ids are visibly invented and the addresses use `example.invalid`. The test key
   follows the existing `sk_test_not_a_real_key` pattern. There is no local path, person or real id in the diff or
   the commit message.
8. **The tests fail without the fix.** The implementer's red run shows 8 failures, one per new behavior, and the
   stubs throw when Stripe is reached on the wrong path. The order of effects is asserted. LF only: no carriage
   return in the diff. The co-author trailer is present.
