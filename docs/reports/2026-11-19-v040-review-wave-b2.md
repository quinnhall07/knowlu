## Important

**I1. A signed-in account with no subscription reads "Active".** T16 branch, fix in code.
- `settings.js:29` `STATUS_WORDS` has no entry for `none` or `trialing`.
- `settings.js:179` falls back to `"Active"` for any status the table doesn't know.
- The cloud answers `status: "none"` whenever an account has no entitlement row (`entitlement/handler.ts:22`; `EntitlementStatus` in `_shared/entitlement.ts:19`). `account_status` passes that through from its cache (`account.rs:1179-1188`).
- Scenario: a student signs in, never finishes checkout, and opens Settings. Membership says "Active" and shows Manage subscription. The shipped row printed the raw status (`console.js:2219`), which was honest. This is a regression, and it is about money.
- Why it was built this way: pin 13 bans the substring "trial" in `settings.js` (`ui_settings.rs:61`), so the builder couldn't write a `trialing` key and used a fallback instead. The fallback also catches `none`.
- Fix, red first:
  - Narrow the pin to ban "trial" as a whole word or in display strings only, so the status code `trialing` may appear.
  - Add `trialing: "Active"` and `none: "No subscription"` to the table.
  - An unknown status reads as neutral, for example "Membership" with no hint, never as "Active".
  - Add a `none` answer to `t16-settings-answers`.

**I2. "Renews <date>" is a claim the data cannot support.** T16 branch, fix in code.
- `settings.js:182` writes "Renews <date>" whenever the status reads "Active".
- `account_status` carries `status`, `plan`, `current_period_end` and `checked_at`, and nothing about cancellation (`account.rs:1179-1188`; the cloud's 5-value enum).
- A subscription cancelled at the period's end stays `active` until it lapses.
- Scenario: a student cancels in the Stripe portal. Settings tells them it renews on 12 Dec, and they think the cancellation failed. The shipped row showed no date at all.
- Fix: use the same wording for every status, for example "Through 12 Dec", or drop the date for active and trialing. Keep "Through" for past_due, canceled and tester.

**I3. A failed update check is ignored entirely.** T19, fix in code. The builder's ruling does not hold.
- `update.js:72` `renderUpdateOffer` begins `if (u.error) { return; }`.
- The ruling assumes an error reply carries no offer. It does: every `check_for_updates` reply has `version`, `staged` (already gated on a running slot), `held`, `last_check`, `last_error` and `action_error`, error or not (`commands.rs:739-760`). The shipped page rendered from it on every reply (`console.js:435-474`).
- Scenario 1: the launch's quiet check fails offline. `UPD.text` is never set, so the Updates row reads "version 0.4.0 — not checked yet". That is false: it was checked and it failed. M8 requires the row to show the check's error. After an earlier success the row keeps saying "up to date" instead.
- Scenario 2: a slot starts, so the reply's `staged` is null and `held` is set. The check also errors. `#top-note` keeps offering Restart to update for a bundle the run is holding back.
- Fix: remove the early return. The existing `UPD.installing || (quiet && UPD.note)` guard already protects install messages. The reply's `staged` is the truth, so a failed check clears an offer only when the updater says nothing is offered.

**I4. Two names from §7's `ui_account_privacy.rs` row are missing, and §7 says a missing name blocks the swap.** T20, fix in the test file.
- `settings_starts_nothing_new_while_the_update_is_owed` is missing. T20's half of it: "while owed, `KnowluKit.owed` disables every `data-start` control and leaves delete and disconnect free".
- `the_panels_changes_name_gmail_and_amazon` is missing. Its assertion was folded into `the_panels_changes_describe_this_privacy_version` (`ui_account_privacy.rs:227-236`).
- The `report*`/`up-*` half of `every_control_this_task_added_is_in_the_markup_and_named_by_the_page` has no counterpart. Its no-duplicate-id check is gone for these three files; T16 kept one for `set-*`.
- Everything else counts out:
  - T16: 11 of 11 re-homed, plus 4 new and the `set-*` half.
  - T17: 38 of 38, plus 5 split halves and 2 new.
  - T18: 9 of 9, plus 2 new.
  - T19: 11 of 11, plus the split half, with the refused-slot words in `sync_line_copy_is_verbatim…`, plus 2 new.
  - T20: 13 of 15.
- The behaviour is mostly still covered by `every_start_control…` and T17's `sources_start_controls_are_marked_and_owed`. The names are what the swap's tick list needs.
- Fix: add the two named tests, the first scanning `data-start` lines plus delete and disconnect. Add a `report*`/`up-*` ids test with the duplicate-id check.

1. **Faithful carry.**
   - Every command the old panels used is called with the same arguments and Tauri's camelCase (`addressId`, `ageAttested`). Nothing is dropped except `open_profile`, `dropped_events`, `mark_seen` and `open_issue`, which belong to other tasks.
   - The handled states match the shipped page, sometimes better:
     - an unreachable service;
     - a busy guard on every door;
     - Check now's "already checking";
     - a refused write that keeps the draft;
     - the conflict draft;
     - the two-step disconnect and delete;
     - Leave versus Stop;
     - the held M365 backfill;
     - "changed since".
   - The gaps are I3, M3, M5 and M6.
2. **Credentials and privacy.**
   - No token, code, password or secret is in an answer. Every `account.rs` reply is ok, error, account id, email or status. So none reaches the DOM, `KnowluData.last` or `ev()`.
   - The only `ev()` calls are `edit_*` (object kind only) and `sync_run`. There is no `console.log` and no storage.
   - The mail flow matches M10 and the shipped flow: the school sign-in happens in the app's window, and the page only gets the address and copies it through `copy_text`.
   - Re-consent keeps the shipped text. "AI" stays verbatim because it mirrors `site/privacy.html:54` and §5 pins the change text. The ruling holds.
   - Delete sends `{}` and is free while owed. The report sends exactly what is in the box, with Send off until a preview lands.
3. **Pins.**
   - Every pin goes through `fn_body`, `rust_const` or `changes_table`, all of which panic on a placeholder, so I found none that passes on one.
   - The casing pins keep the engine's words lowercase (`SYNC_SAYS` verbatim), with `cap()` and `::first-letter` capitalising for display. The ruling holds; see M12 for the button labels.
   - The launch check calls `account_status`, then `privacy_status` only when `s.ok && !s.needs_account`, both through `KnowluData.call`.
4. **The shared surface.**
   - All five sections (sources, week, status, updates, report) register with `KnowluRouter.addSection` and mount through T16's `mount(host, api)`.
   - `#settings/sources` works: the router remounts on a changed argument, `sources.js:28` draws `data-section="sources"` synchronously, and `goSection` runs on the next animation frame. `#settings/data`, `/week`, `/day` and `/status` resolve the same way.
   - Every start control carries `data-start` with `KnowluKit.owed()` inside `owedHtml`. The update line uses `#top-note`.
   - CSS: see M15.
5. **No price, no "trial".** Reading "Active" for a trialing account and showing no price in Membership is acceptable under A2. It is not acceptable while `none` also reads "Active" (I1) and "Renews" stays (I2).
6. **Focus, labels and live regions.** Fix the dark-theme fill once in `shell.css` (M1). Also see M4, M9 and M10. Settings headings take focus on `#settings/<section>`, and every focus ring I checked is present.
7. **No real person's data.**
   - The envelopes use `example.edu` and `example.net`, the vault "D:\Knowlu vault", the profile "School", the registrar label "Campus portal", course codes ABC, DEF and JKL, and buildings named "Hall 4". "Hall" there is a building, not a surname.
