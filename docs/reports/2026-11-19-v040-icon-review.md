## Findings

### Important

**I1. `app/icons/icon.ico` directory entry 0 is the 16 px image. Tauri builds the runtime window icon from entry 0.**
Rule: app correctness ("fix the app icon"). Not a CLAUDE.md invariant.

- `tauri-codegen-2.6.3/src/image.rs:56-61` (`new_ico`) decodes `icon_dir.entries()[0]` and nothing else into
  the context's `default_window_icon`.
- `tauri-2.11.5/src/manager/window.rs:75-76` applies that icon to every window.
- `tauri-runtime-wry-2.11.4/src/lib.rs:1245-1248` passes it to tao as `with_window_icon`.
- `tao-0.35.3/src/platform_impl/windows/window.rs:882-890` sets it as `ICON_SMALL`. Tauri sets no `ICON_BIG`
  and tao registers no class icon (`hIcon: HICON::default()`, window.rs:1365).

The new file's directory order is 16, 20, 24, 32 … 256, with entry 0 at 16x16. The old placeholder's single
entry was 32x32. So the window's own icon dropped from 32 px to 16 px. The resource icon the controller
checked (256 px, extracted from the exe) is a different path. Explorer, shortcuts and the installer use the
resource icon. The live window does not.

Failing scenario: a student's laptop runs at 150% or 200% scaling, the common default on laptops. Windows
then wants a 24 or 32 px small icon. It stretches the 16 px bitmap, so the Alt+Tab icon is blurry, and so is
any taskbar or switcher surface that falls back to the window's small icon because no big icon is set. That
is the opposite of "use the high-def icon". Tauri's own `tauri icon` generator puts the 32 px entry first for
this reason. Winit/tao's docs for the window icon recommend 32x32 to cover scaling. I did not run the app at
150%, so whether the taskbar itself shows it depends on the shell's fallback. The Alt+Tab small icon does not
depend on it.

Fix: reorder the ICO directory so the 32 px entry comes first. The ten PNG payloads stay byte-identical; only
the 16-byte directory records and the offsets move. A Pillow re-save does not guarantee the order, so do it in
`scripts/brand-icons.py` or by hand. Add a pin to `the_app_icon_is_an_ico_holding_every_size_windows_asks_for`
that entry 0 is 32 px. The script's docstring and the README then say "byte-for-byte except directory order".
Check by running the dev exe at 150% and comparing Alt+Tab before and after.

## The five questions

1. **tray.rs is correct.**
   - `Image::new(&'a [u8], u32, u32)` is a `const fn` that borrows (`tauri-2.11.5/src/image/mod.rs:63`). With
     `include_bytes!` statics, `&'static [u8]` gives `Image<'static>`; no lifetime issue.
   - Conversion to `tray_icon::Icon::from_rgba` copies the bytes (`to_vec`, mod.rs:154).
   - `tray-icon-0.24.2/src/platform_impl/windows/icon.rs:26-47` swaps RGBA to BGRA itself and calls
     `CreateIcon` at 32 bpp. 32 bpp icons take straight (non-premultiplied) alpha. Pillow's
     `convert("RGBA")` of a PNG is straight alpha. Row-major order and 4096 bytes match `Image::new(.., 32, 32)`.
   - Mapping: Ok gives `TRAY_OK` at build (`tray.rs:38`) and in `set_state`; Warn gives `TRAY_WARN`
     (`tray.rs:149-152`).
   - The two callers, `scheduler.rs:1122` and `:1260`, are untouched, and the menu, menu events and the
     tray event handler are unchanged.
   - The amber contract holds: tray-warn has opaque `#d9a441` pixels, and tray-ok has none.

2. **PNG-compressed entries below 256 px are fine.**
   - `rc.exe` copies each ICO payload into an `RT_ICON` resource unchanged.
   - `LoadImage`/`CreateIconFromResourceEx` decode PNG payloads at any size from Vista on. Explorer and the
     taskbar load through those calls.
   - The "PNG only at 256" guidance exists for Windows XP and for load cost. Neither matters for a Windows 11
     desktop app.
   - NSIS 3.x accepts PNG entries. It also dropped NSIS 2's rule that the uninstaller icon must match the
     installer icon's formats. `makensis` 3.11 already built with this file.
   - tauri-codegen's decode runs at compile time and panics on failure (image.rs:58-60), so a green build
     already proves the `ico` crate reads these entries.
   - `wPlanes` is 0 in every entry. That is legal, and with all ten entries at 32 bpp, selection goes by size
     alone.
   - I know of no reason to re-encode the small sizes as BMP. The pre-tag `release.ps1 -DryRun` (full bundle)
     is the right last check. The real icon problem is the entry order (I1), not the encoding.

3. **The set_state pin's slicing is not brittle enough to matter.**
   - Squashed, the slice runs from `pubfnset_state(` to `redact`'s `///`. If that doc comment moves or goes,
     the slice runs to the end of the file. The pin then gets looser, but it never fails falsely, and the two
     arm strings appear nowhere else.
   - A swapped mapping (`Ok=>tray_icon(TRAY_WARN)`) still fails.
   - A refactor through a helper fails loudly, not silently. Fine as it is.

4. **`.gitattributes` has no interaction problem.** `binary` is `-text -diff -merge`.
   - `git ls-files --eol` shows `site/favicon.ico` as `i/-text`. Its index bytes do not change, and an ICO
     header's zero bytes already kept it binary under `text=auto`.
   - `eol-check.ps1` flags only `i/crlf` or `i/mixed` outside fixtures and `.ps1`, so `-text` files pass.
   - No `.ico` or `.rgba` file lives under `engine/tests/fixtures/`, so the `-text` fixture rule is unaffected.
   - The attribute matters for `tray-ok.rgba`. It contains no zero bytes (`i/none`), so without `binary` a
     future regeneration that happens to contain `0D 0A` would be classed as text and normalised by
     `* text=auto eol=lf`.

5. **Contract list and config are untouched.** Nothing on CLAUDE.md's contract list is touched, and
   `tauri.conf.json` is unchanged. There is no single-user path in `scripts/brand-icons.py`. The diff adds no
   data class, telemetry, logging or credentials. The gate result is as reported by the dispatch (3385
   passed, 3 ignored, .rsrc only, eol holds); I did not run cargo.
