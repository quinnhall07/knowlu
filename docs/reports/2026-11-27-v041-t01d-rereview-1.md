## First-review findings

### Finding 1 (a 2xx whose body is `null` was read as "unknown" and purged past): fixed

`cloud/supabase/functions/account/stripe_delete.ts:94, 126, 157-158`

How the fix works:
- `getOrMissing` builds a fresh `deleteFetch` for each call. Its `onMissing` callback sets a local flag, and it is
  called only on a 404 whose code is `resource_missing` and whose message is not the other-mode text.
- `stripeGetFrom` returns `null` for a non-2xx without reading the body. The only non-2xx that `deleteFetch` lets
  through is that bodiless 404, so `"missing"` means exactly that the 404 arrived.
- Any other `null`, such as a 200 with the body `null`, now reaches the shape check, which requires a non-array object
  with a string `status`. It throws the 502.

Concurrency: the flag is per call, so two concurrent deletes cannot share it.

Tests: six new read cases (`null`, an array, a string, a number, `true`, an array holding a status) each give the 502
with a clean log. The implementer's red run shows the `null` case failing against round 0.

### Finding 2 (the stored id can lag Stripe; adopt the list by customer): fixed

`cloud/supabase/functions/account/handler.ts:107-120, 139-170`; `stripe_delete.ts:186-218`

I checked each bullet of the brief:

- **When it lists.** `settled` becomes true only after a live stored subscription has been set to cancel. Every other
  stored state lists when `account.stripe_customer_id` is set: ended, unknown to Stripe, or no stored id. That covers
  the review's scenario.
- **The customer id is stable.** `billing-checkout/handler.ts:348-356` saves the customer before the first session and
  reuses it after that, so a former subscriber's new subscription sits on the stored customer and the list sees it.
- **The list is the whole list or nothing.** It must be an object with a `data` array and `has_more === false`. An
  absent or non-boolean `has_more` is refused too. Every item needs a `sub_`-shaped `id` and a string `status`.
  Anything else, any non-2xx other than the real `resource_missing` 404, a thrown fetch and a non-JSON 2xx all give
  the 502 before the purge.
- **What gets cancelled.** Every item whose status is not `canceled` or `incomplete_expired`, and whose
  `cancel_at_period_end` is not exactly `true`, is set to cancel. That includes a status the code has never seen. The
  first refused update stops the delete (test at `handler_test.ts` ~line 498).
- **An unknown customer.** Only the real 404 `resource_missing` counts. The other mode's 404 is the 502.
- **No customer and no stored id:** no Stripe call.
- **A live stored subscription:** one read and one update, no list. A test pins this with a list stub that throws.
- **Shape checks.** The customer id is checked against `^cus_[A-Za-z0-9]+$` before the query, and an empty column
  means no customer. Each listed id is checked against `SUBSCRIPTION_ID` before it goes into an update path.
- **Logs and responses.** All the new log lines are fixed text with no id in them. The caller only ever gets the fixed
  502 text. The pinned `Stripe-Version` goes on the list (asserted in the test).
- **Order of effects.** A failed list, with or without a stored id, leaves only the read and the list: no purge,
  tombstone or login delete. The end-to-end scenario runs read, list, cancel `sub_2`, then the purge.

## The specific hunts

- **Does any Stripe answer besides the accepted ones reach the purge?** No. The read accepts a string status or the
  real 404. The list accepts the exact whole-list shape or the real 404. An update must succeed. Everything else
  throws before `deps.purge`.
- **Can a listed item that can still charge be skipped?** Only when `cancel_at_period_end === true`, which the brief
  allows. An unknown status is cancelled.
- **Does an id go into a path or query without its shape check?** No. The stored `sub_` id, the stored `cus_` id and
  every listed `sub_` id are checked, and each is also encoded.
- **Does an id or Stripe's raw body reach a log line or the response?** No. A refused body is logged only after
  `redactStripeText`, and the missing-404 body is never logged.
- **Did the live stored-subscription path change?** No, apart from the update being moved into a helper with the same
  path and form.
- **Are the implementer's rulings safe?** Yes. Each fails closed:
  - the strict list shape;
  - `has_more` stops the delete;
  - an id that is not subscription-shaped stops the delete instead of being skipped;
  - only an explicit `true` counts as already cancelling;
  - an unknown customer means nothing to cancel. That one is safe on the charge rule because Stripe cancels a
    deleted customer's subscriptions with it. The different-Stripe-account caveat recorded in the first review's
    finding 3 applies here too.

## New findings

No Critical or Important finding. The Minor items below do not block.

### A. Minor: an unknown customer may not come back as a 404

`stripe_delete.ts:198` (a `resource_missing` passes only at status 404, `:93`)

The implementer's concern 1 is right, and it is unverified on my side too. For an id passed as a query parameter,
Stripe may answer 400 `resource_missing` (`param: customer`), not 404.

Failing scenario: an operator deletes the customer in the Stripe dashboard (on staging, say). That student's Delete
my data then stops at the 502 on every attempt, so the deletion right is blocked.

This fails toward safety, not toward a charge. Recommendation: the staging proof lists subscriptions for a deleted
customer and an invented `cus_` id. If the answer is a 400 `resource_missing` with `param: customer`, the controller
rules whether to accept it, as the other-mode exclusion was ruled.

### B. Minor: an id with `_secret_` in it survives the widened redaction

`stripe_delete.ts:41`

A client secret such as `pi_3AbC_secret_dEf` has no word boundary inside it, so `STRIPE_ID` never matches. These
three calls (a subscription read, a list, a `cancel_at_period_end` update) have no realistic error body that carries
one, and the brief's rule (no subscription or customer id) holds. The commit message's claim that "every other Stripe
object id" is stripped is slightly too broad. If wanted, it is a one-line fix: also replace
`/\b[a-z]+_[A-Za-z0-9]+_secret_[A-Za-z0-9]+/g`.

## Residual gaps this round did not open (for the controller, not this task)

These two existed before T1d and remain. Each can still lead to a charge after the account is gone.

1. **A second live subscription behind a live stored one.** `handler.ts:160-163` lists nothing once the stored
   subscription is live, as the brief ordered.

   Failing scenario: D5 reads `entitlements`, which lags. A student completes Checkout, then subscribes again before
   the first webhook lands, and ends up with two subscriptions. The delete cancels the stored one, and the other
   keeps charging.

   Recommendation: always list when a customer id is stored, and cancel every live one. That costs one GET per delete
   and closes this case.

2. **A Checkout page still open at delete time** (the implementer's concern 3). The student deletes their data, then
   completes a page that was still open. That creates a subscription on the stored customer with no account behind
   it.

   Recommendation: run T1b's `expireOpenCheckouts` for the customer inside the delete, before the purge, and stop at
   the 502 if it fails.
