## Cost and risk in the ordinary case

- A first press makes no new call. Every later press, from any account that has pressed Subscribe before (including one that left its page unpaid), makes one extra Stripe GET plus one POST per open page. With fewer than 100 open pages that is exactly one list call. The step never waits for Stripe's list to catch up, because a short list ends it.
- **What an outage does to sales.** Before this task, a returning customer's checkout needed Stripe's price GET and the session POST. Now it also needs the list GET. If the list endpoint fails or rate-limits (a 429), **every returning customer is refused with a 502** until it recovers. First presses still go through. A broad Stripe API outage already stopped sales, because the price GET and the session POST were in the path, so the new exposure is only an incident that hits the list endpoint alone. Failing closed is the right trade: the harm this step prevents is a second subscription that keeps billing after the account is deleted, and a refused press costs one retry.
- **The 502s** follow the handler's existing provider-failure convention: status 502, `{"error": "<lowercase sentence>"}`, the same shape as `the payment provider returned no customer id`. Each one names its reason. The app shows the sentence exactly as given (`app/static/js/wizard.js:718`, `carried/account.js:208`, through `provider_error`) and asks for the offer again. None of the three tells the student what to do next (M4).

## Stripe calls

- The list path is `/v1/checkout/sessions?customer=<encoded>&status=open&limit=100`. The customer id comes from our own database and is encoded. `openCheckoutsPath` is tested with an id that tries to smuggle in `&status=` and `&starting_after=`, and both arrive encoded.
- The expire path is `/v1/checkout/sessions/<encodeURIComponent(id)>/expire` with an empty form. The id comes from Stripe's reply and has already passed the customer and status checks. Encoding stops `/`, `?` and `&`. It does not stop a whole id of `.` or `..`, which WHATWG URL parsing collapses as a dot segment (M5, hardening only).
- As far as I know Stripe's API reference: the list endpoint accepts `customer`, `status` (`open | complete | expired`) and `limit` up to 100, and returns sessions newest first, with `customer` as an unexpanded id. `POST /v1/checkout/sessions/{id}/expire` succeeds only on an `open` session and answers a 4xx otherwise. Expiring a session emits `checkout.session.expired`, which `stripe-webhook/handler.ts:209-214` acknowledges with a 200 and ignores, so the expire has no side effects on our side.
- `stripeGetFrom` returns `null` on every non-2xx, a 404 included, and the handler treats `null` as a failure, never as "no sessions". "No sessions" can only be a 2xx with `data: []`. A network error or a non-JSON 2xx throws, is caught and refused. The production dependency behaves as the fake does.

## Findings

**M1 (Minor). The step cannot close windows outside one request.** `handler.ts:352-356`. (a) Two concurrent POSTs for one account: each list call runs before the other's session exists, so both create a page and both pages stay open. Each UI's `checkoutBusy` prevents this within that UI, but not across two installs or between the wizard and the sheet. (b) Page A is completed, and the student presses again before the webhook writes `entitlements`. A is now `complete`, not `open`, so it is not listed. D5 sees no subscription, so a second page with a trial is created and can be paid. Both cases lead to the harm the task exists to stop, and both are outside the binding rule. Smallest fix, as a separate task for the founder to decide: a webhook backstop that cancels a newer subscription when `checkout.session.completed` arrives for an account that already has a different live subscription id.

**M2 (Minor). The bound's edges.** `handler_test.ts:1042-1052`. If the bound were deleted, the test would hang instead of failing, because the fake answers fresh sessions forever. The comment's claim that "five rounds clear up to 499" (`handler.ts:51`) is untested: code that refused on the fifth round even when that list was short would pass. Fix: make the bound block's fake throw after 2 × `OPEN_ROUND_BOUND` calls, and add a block with four full lists of new sessions and then a short list, which must end in a 200 with 5 list calls and 401 expires.

**M3 (Minor). Branches with no test.** `handler.ts:105`: removing the duplicate check (`!fresh.includes`) fails no test. A session with an id but no `customer` is not tested on its own. The existing case at `handler_test.ts:896` fails on the missing id first. Nothing open is never shown to cost exactly one list call, because the default fake does not record the list. Fix: three small cases. A list holding `cs_open_a` twice must expire it once. A session with an id but no `customer` must give a 502 with no expire. An existing customer with nothing open must record exactly one list call.

**M4 (Minor). The student cannot act on the three sentences.** `handler.ts:63-65`, shown as given by `wizard.js:718`. "the payment provider's list of open checkout pages did not end" names a reason but tells the student nothing to do. The brief asked for the provider-failure shape, and the existing 502s have the same problem, so this is the founder's call, not a defect. If the founder wants a change, the smallest one is to add "; try again in a minute" to all three.

**M5 (Minor, hardening). Session ids from Stripe's reply are not checked for shape.** `handler.ts:99`. A whole id of `.` or `..` survives `encodeURIComponent`, and the URL parser resolves it as a path segment, so the empty-form POST would go to `/v1/checkout/sessions/expire` or `/v1/checkout/expire`. This needs Stripe itself to send such an id, and it fails closed, so the risk is theoretical. Fix: require `/^cs_[A-Za-z0-9_]+$/` in `openSessions` and refuse the list otherwise.
