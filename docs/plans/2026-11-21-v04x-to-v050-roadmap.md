### 2.1 In v0.5.0

**A. The first session** (`VISION.md:197`, success 5; `:198`, success 6), on Windows and on a Mac:

## 3. The constraints that shape the order

1. **Each release is whole.** A student who updates gets something that works. Nothing is shown as "coming"
   in the app (`docs/specs/2026-11-17-v0.4.0-new-ui-design.md:92`). Each release ends in a `v*` tag pushed
   on Quinn's word, built and signed by CI.
2. **What merges to `main` ships in the next tag.** So a pull request for release N+1 merges after tag N.
   Docs-only merges are exempt. Work for N+1 is built and reviewed while N is in flight, then held.
3. **One privacy change per build.** A test pins exactly one `PRIVACY_CHANGES` key, the build's
   `PRIVACY_VERSION` (`app/tests/ui_account_privacy.rs:227-233`). The page is version 2026-10-20 today
   (`app/src/account.rs:25`, `site/privacy.html:12`). Section 5.1 plans seven bumps, each in a different
   release, and says how each avoids one more.
4. **`app/src/account.rs` is on the contract list and is edited one piece at a time.** In order: v0.4.1
   (T4a, T5), v0.4.2 (the privacy bump, C1), v0.4.4 (the site table at `:1696`, the portable seams),
   v0.4.10 (the relay's bump), v0.4.13 (the bump, the sign-out work from the onboarding branch), v0.4.17 (only if a second school
   system's kept sign-in adds to the sign-out cleanup; `unverified`), v0.4.22 (the gift's bump), v0.4.23
   (Keychain, the bump), v0.5.0 (the bump, the offer's trial fields). No two of these run side by side.
5. **v0.4.1's T4 owns `app/static/js/wizard.js`, `pages/settings.js` and `carried/account.js`,** and
   with them `app/tests/ui_wizard.rs`, `app/tests/ui_settings.rs` and three ui-fixture checks (the v0.4.1
   plan's task table, on branch `docs/v041-pricing`). Everything that touches them lands after v0.4.1.
6. **The frozen references.** The eight Python-written references are never regenerated. The three
   `surface-today-*.json` references change only in a commit whose diff shows the change and whose message
   says why. New read-model data is added so they stay byte-identical: a region that is never emitted on
   the today view, as `list` is carried only by the four horizon views (`engine/src/surface.rs:2376-2377`),
   or one omitted when empty, as `courses` and `grades` are (`:2359-2368`). `closed_this_week` is empty in
   all three (section 0, item 5), so fields added to a closed row change none of them.
7. **Two pieces have a gate of their own, and nothing else may depend on either.**
   - The vendor-host syllabus read is ruled: build and ship regardless (rulings 8 and 11). The vendor's
     terms, as read on 2026-10-20, bar automated harvesting without written permission
     (`docs/notes/2026-10-20-simple-syllabus-terms-first-read.md`). That stays on record and goes to the
     lawyer. The other two sources `VISION.md:88-89` names, a syllabus found in the LMS or a file the
     student adds, are not under that bar. Every release that uses syllabi works on those two alone, so
     the host read can be switched off per school, as data, if the vendor objects or blocks it.
   - Entering the saved school password on the school's page is ruled: build it, opt-in (ruling 5). A
     safety classifier stopped that task on 2026-11-08 before the ruling (section 0, item 7). It is now
     built as Quinn ruled it, as its own Contract piece in v0.4.13, with the opt-in wording read by Quinn.
     Every release that uses the school sign-in works without it. If it cannot be built or proven, the
     fallback ships alone and the item returns to Quinn; nobody rewords the task to get it through.
8. **Rulings that exist only in chat are signed before the spec that rests on them is reviewed.** Five
   drafts wait for Quinn's signature (5.6): the Mac, the sales gate, the onboarding and the school
   sign-in, the new semester, and the relay's move ahead of Launch.
9. **No single-user assumptions.** Nothing in any release names one school, person, account or machine.
   Every site is added through a table, never a branch on a name.
10. **Mac needs its signed amendment before its first line of work.** `VISION.md:150` says "A Windows
    desktop app" and `site/terms.html:16` says "Knowlu is a Windows app". Ruling 19 approves the new
    sentence; the signature line in a docs PR is still owed.
11. **No CI job builds anything off Windows today** (`.github/workflows/ci.yml:75`,
    `.github/workflows/release.yml:30, 275`). "It compiles on macOS" is unproven until a macOS runner says
    so (section 0, item 14).
12. **One Windows laptop, at most four builds at once, no Mac at hand.** Live proofs drive the DOM only,
    against staging. Production only on Quinn's word. No subagent holds a session.
13. **Sales.** No release before v0.5.0 opens buying to anyone new. v0.5.0 does (ruling 16; 2.3).
14. **Proofs need live courses.** Ruling 6 asks for a real student account on each site. Quinn knows at
    least one student for every site, this term and next (ruling 40). So a proof on a live course can
    run this term, before finals in mid-December, for whatever is built in time. Everything built later,
    the new-term check (T-07) and v0.5.0's own proof run in the spring term, which by Quinn's date
    starts on January 11 (rulings 38 and 42). Which friend has which site next term is confirmed again
    at each sitting.
15. **Two dates are set in signed text.** The pilot starts in spring 2027 and the official launch is fall
    2027 (`docs/specs/2026-09-09-knowlu-cloud-design.md:806-812`). Recruiting started in November 2026
    (`HANDOFF.md:479`). Quinn has given one more: January 11, the day spring classes start, which is the
    new-semester core's deadline and the last day of the "free forever" offer (rulings 38 and 42). This
    plan gives no other date.
16. **Every sign-in reader after v0.4.10 is built on the relay** (ruling 30). The device keeps the
    student's login and a compiled-in table of the hosts each login may be sent to; the cloud says which
    pages to fetch and reads what comes back (`docs/specs/2026-09-17-c5-relay-fetch-design.md:33-45`).
    A reader that breaks is repaired by a cloud deploy. A new site's hosts and its login panel still
    cost a release (`:506-510`).

### 5.2 Step 0: the Thanksgiving checks (ruling 24)

**What it is.** Discovery, with no Knowlu account. For each of the twelve sites a friend uses this term:
every route by which its work could reach Knowlu, not only the first that works (ruling 25). Nothing is
installed for the friend, nothing is signed up, nothing reaches Knowlu's cloud.

**What it needs first.**
1. **The script.** It is built: `scripts/site-check/feed-shape.mjs`, with its tests and its README
   (PR #85). Node 20 or later, no install and no dependencies. Every feed in its tests is made up and no
   test touches the network. It had its own two reviews. What follows is its README, and nothing the
   README does not say.
2. **The sheet.** It is this section: the questions, in the order a sitting meets them.

**What the script does (PR #85's README).**
- **How it takes the link.** It asks `Paste the calendar link, then Enter:` and the friend pastes the
  link themselves; on a terminal the pasted text is not echoed. The link is read from one line of
  standard input and never from the command line, so it stays out of the shell history and the process
  list. It is never printed, logged or written. An error names the HTTP status or the kind of failure,
  never the link or any part of it. A feed link is a capability: whoever holds it reads the student's
  schedule (`app/src/lms_link.rs:299-301`).
- **What it refuses.**
  - A link typed on the command line. It refuses without repeating it. That link is then in the shell
    history, so the friend resets the feed link in the school's system and pastes the new one when
    asked.
  - Anything that is not `https` (`webcal://` is read as `https://`).
  - A fetch that takes more than 20 seconds or passes 20 MB.
  - A redirect to anything but an `https` address. It does follow up to 5 redirects to `https`
    addresses, so it can contact a host other than the link's own.
- **What it keeps.** Nothing. It never writes a file; the report goes only to the screen.
- **What the default report prints.** Totals; the property names on items; UID shapes; class counts,
  as `class 1`, `class 2` and so on; outside-site markers per site; and title endings. It holds counts,
  dates, times of day, property names and UID shapes. By default it shows no text from the friend's
  items: no titles, descriptions, locations, class names or `X-` values.
- **The site markers** are counted against a fixed table of thirteen sites: the eleven homework sites on
  the strip, plus the two Knowlu reads today. A name match is a hint, not proof, and a count of 0 does
  not prove a site is absent, because its items may carry no marker.
- **What a UID shape can still show.** The host after the UID's last `@`, as written, when it is a plain
  host name and at least two items share it; that is usually the school's site host. Otherwise the host
  shows as `<host>`. Punctuation and a fixed list of structural words stay (among them `gradableitem`,
  `blackboard`, `calendar`, `assignment` and `due`); every other word becomes `<w>`, a run of digits
  becomes `#`, and a UUID or a long run of hex becomes `<hex>`.
- **`--show-titles`** also shows item titles and real class names. It is for eyes at the sitting only:
  its output is never saved, pasted or shared.
- **Other options.** `--file <path>` reads a saved `.ics` file instead of fetching. `--now YYYY-MM-DD`
  sets the day the before-and-after counts use. `--json` prints the same summary as one JSON object.
- **Exit codes.** 0, a report was printed. 2, bad input or a refused link. 1, the fetch failed,
  including a redirect the tool refused.

**What the script does not do, and how the sheet copes.**
- The paste check and a list of unknown link hosts are not in the script. F1 rests on its fixed site
  table, and "which class uses which site" is asked by eye, or with `--show-titles` on screen only.
  Whether a link passes Knowlu's own paste check (`app/src/lms_link.rs:302-307`) is learned at the proof
  inside Knowlu.
- It prints no count of the gradebook-item shape Knowlu already joins (`engine/src/ingest.rs:567`) or of
  the noise marker Knowlu already drops (`:225`). Both are read by eye from the UID shapes, because the
  masking keeps the words that mark them.

**What ruling 44 settled, and what it left.**
1. **Ruled:** a fallback reader stays idle while the first route is healthy. That keeps to ruling 33's
   purpose: Knowlu does not sign in to a publisher when it need not.
2. **Not ruled:** what counts as a route having "gone quiet" without an error: the number of quiet days,
   and whether it differs by site. Quinn answered this point with the report of part G instead. The
   sites spec defines "gone quiet" and puts it to Quinn at its checkpoint.
3. **Ruled:** a failed route still shows as failed wherever sources are listed (Settings, a class page's
   Sources row, the run log). That keeps `VISION.md:182` true: "Failures are visible; silence is never
   ambiguous." What ruling 34 removes is the interruption.

**Part G, the report to Knowlu (ruling 44), placed and sized.** Its purpose is Quinn's: "we know if
something's not working for just one user OR if it's just down in general."
- **What is sent,** once for each run in which a route fails: the site, the route (F, G, M, S or K),
  the kind of failure from a closed list the sites spec fixes (for example: sign-in refused, page not
  found, nothing parsed, timed out), the build version and the time. It is keyed to the account, as
  every telemetry row is (`cloud/supabase/migrations/20260910000400_telemetry.sql:10`).
- **What is never sent:** content. No title, class, score, link, address, page text or login. Every
  field is a token from a closed list, and the server refuses anything else, as the telemetry function
  already does for its own rows (`cloud/supabase/functions/telemetry/handler.ts:1-15`).
- **Who sends it.** The app, beside the telemetry it already derives on the device and sends with each
  slot (`app/src/telemetry.rs:1-7`; `docs/reference/app.md:259`), from the route health of part A. The
  engine's commands are unchanged: `coursework`, `judge` and `sync` still exit 0 and a failure is still
  a named outcome. Whether an existing row already carries a slot's outcome is `unverified` (`sync_run`
  is one of the eleven actions, `engine/src/uievents.rs:13`); the sites spec opens it.
- **Where Knowlu sees it.** One view that counts failures by site, route and kind, per day, with the
  number of accounts affected. One account means one student's problem; many mean the site is down or
  changed. It needs a table or a view of its own. The one view a dashboard may read today hides any
  group smaller than ten accounts, on purpose

- **How long it is kept:** with telemetry, which C4 deletes after two years, unless the sites spec sets

- **What it is not.** It is not an alert, and nobody is paged: no alerting is built unless the sites

### 8.2 Stop rules

Work stops and the question goes to the main session, and from there to Quinn, when:
1. A step would regenerate a Python-written reference, or one of the three read-model references changes
   outside its rule.
2. A piece sized Small or Lane turns out to touch the contract list, a vault byte format, a migration,
   money, credentials, a release or the privacy page. It is re-sized as Contract before it continues.
3. A build would need a second privacy key.
4. A site's proof is anything other than a real student in a live course. The site is not flipped.
5. A safety stop halts a task. Nobody rewords the task to get it through.
6. A test, fixture, report or commit would hold a real student's class, grade, title, login or link, or a
   feed sample would be placed under `engine/tests/fixtures/**`, or the report of a failed route would
   carry anything but a token from its closed list (ruling 44).
7. A proof or a deploy would touch production without Quinn's word at the time.
8. A spec rests on a ruling that is not yet signed. Its review waits for the signature.
9. A first route would touch a publisher, a fallback would sign in without the student, or work would be
   inferred from a route's silence.
10. v0.5.0's tag is asked for with a precondition of 5.30 unmet. Google's approval is the one Quinn may
    waive (ruling 50).
11. A document is still open after its second review. It goes to Quinn as a short list of decisions.
12. After v0.4.4, a new window, credential or path breaks the portable rule, or the macOS job goes red.
13. A spike says no: the Keychain between two binaries, Brightspace grades through the kept sign-in, the
    school sign-on in WebKit, the relay inside a kept sign-in.

After step 0's report (5.3's map becomes results). After the sixth release ships (the pace; ruling 47).
